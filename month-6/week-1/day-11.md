# Day 11 — Password Reset Security

## Concept

What is password reset?

Password reset is a process that allows a user to regain access to their account when they have forgotten their password. The application must verify that the person requesting the reset is the legitimate account owner.

## Password Change vs Password Reset

Difference between them.

**Password Change:**

* The user is already authenticated.
* The user provides their current password and chooses a new password.

**Password Reset:**

* The user cannot authenticate because they forgot their password.
* The application must verify the user's identity before allowing a new password to be set.

## Secure Password Reset Flow

1. User requests a password reset for their account.
2. The application generates a secure, unpredictable reset token.
3. The reset token is sent to the legitimate user's registered email or other trusted channel.
4. The application validates the reset token when the user submits the new password.
5. The password is changed only after successful token validation.

## Reset Token

What is it?
Why is it important?

A reset token is a security value generated by the application and provided to the user as part of the password-reset process.

It is important because it helps prove that the person performing the password reset has access to the trusted reset mechanism. The server must validate the token before allowing the password to be changed.

## Testing Methodology

1. Request a password reset for a test account.
2. Inspect the password-reset requests and responses in Burp Suite.
3. Identify where the reset token is supplied and how it is handled.
4. Test whether the password-reset functionality still works when the token is removed or modified.
5. Determine the security impact and document the vulnerability.

## Lab

Name: Password reset broken logic
Platform: PortSwigger Web Security Academy
Difficulty: Apprentice

## Vulnerability

What was wrong?

The application did not properly validate the password-reset token when submitting the new password. The reset token could be removed while the password-reset request was still processed.

The `username` parameter was also client-controlled, allowing it to be changed from `wiener` to `carlos`.

## Impact

What could an attacker achieve?

An attacker could reset another user's password without possessing a valid reset token and potentially take over the victim's account.

## Evidence

What Burp request demonstrated the issue?

The following request demonstrated the broken token validation:

```http
POST /forgot-password?temp-forgot-password-token=
```

```text
temp-forgot-password-token=&username=carlos&new-password-1=test1234&new-password-2=test1234
```

The request was accepted and returned:

```http
HTTP/2 302 Found
Location: /
```

The attacker could then log in to the `carlos` account using the new password.

## Remediation

How should the application fix it?

* Validate the reset token on the server before changing the password.
* Ensure the token is unpredictable and securely generated.
* Bind the reset token to the correct user/account.
* Make reset tokens expire after a limited period.
* Prevent reuse of reset tokens after a successful password reset.
* Never trust client-controlled parameters such as the username for authorization.

## Key Lessons

1. A security token is only effective if the server actually validates it.
2. Client-controlled parameters such as usernames must not be trusted for authorization.
3. Broken password-reset logic can lead to **account takeover**.
