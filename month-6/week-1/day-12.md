# Day 12 — Password Reset Poisoning

## What is Password Reset Poisoning?

Password reset poisoning is a vulnerability where an application uses attacker-controlled information when generating a password-reset URL.

For example, if the application trusts a manipulated host-related value, an attacker may cause the reset link to point to an attacker-controlled server.

This can cause the password-reset token to be sent to the attacker-controlled destination.

## Normal Password Reset Flow

1. User requests a password reset.
2. The application generates a reset token.
3. The application creates a password-reset URL containing the token.
4. The reset link is sent to the legitimate user's email.
5. The user clicks the link.
6. The application validates the token and allows the password to be reset.

## Reset Token

A reset token is a security value generated by the application for a password-reset operation.

The token is important because it is used to authorize the password-reset process.

The token should be securely generated and should not be exposed to an attacker.

## Host Header

The `Host` header identifies the host that the HTTP request is intended for.

Applications may sometimes use host-related information when generating absolute URLs.

Client-controlled HTTP headers should not automatically be trusted for security-sensitive operations.

## Vulnerability

The application trusted attacker-controlled host information when constructing the password-reset URL.

In this lab, the `X-Forwarded-Host` header could be manipulated.

By changing it to the exploit-server domain, the application generated a password-reset link pointing to the attacker-controlled exploit server.

When the victim accessed the link, the reset token was sent to the exploit server.

## Testing Methodology

1. Establish the normal password-reset behavior.
2. Capture the password-reset request in Burp Suite.
3. Send the request to Burp Repeater.
4. Identify host-related headers.
5. Change only the relevant host-related value.
6. Use an authorized exploit server to observe the generated request.
7. Check whether the victim's browser requests the attacker-controlled destination.
8. Check whether the password-reset token is included in the request.
9. Determine the security impact.
10. Document the evidence and remediation.

## Burp Evidence

Normal request:

POST /forgot-password HTTP/2

The request contained:

Host: [lab-host]

username=wiener

The host-related value was then manipulated using:

X-Forwarded-Host: [exploit-server-host]

The exploit server received a request from the victim:

GET /forgot-password?temp-forgot-password-token=[REDACTED] HTTP/1.1

The request contained a password-reset token.

The request came from the victim's browser:

User-Agent: Mozilla/5.0 (Victim) ...

The `404` response did not prevent the evidence from being useful because the exploit server still received the request containing the reset token.

## Security Impact

An attacker could potentially obtain another user's password-reset token.

If the attacker can use the captured token to reset the victim's password, this could lead to account takeover and unauthorized access to the victim's account.

## Remediation

- Do not blindly trust client-controlled host-related headers when generating password-reset URLs.
- Generate reset URLs using a trusted, server-side canonical hostname.
- Validate and control trusted proxy headers such as `X-Forwarded-Host`.
- Ensure password-reset tokens are securely generated.
- Make reset tokens expire after a limited period.
- Invalidate reset tokens after successful use.
- Prevent reset tokens from being exposed to attacker-controlled destinations.

## Day 11 vs Day 12

### Day 11 — Broken Password Reset Logic

The application did not properly validate the reset token and trusted a client-controlled username parameter.

This could allow an attacker to reset another user's password.

### Day 12 — Password Reset Poisoning

The application used attacker-controlled host information when generating the password-reset URL.

This could cause the reset token to be sent to an attacker-controlled destination.

## Key Lessons

1. Client-controlled HTTP headers should not automatically be trusted for security-sensitive operations.
2. A password-reset URL is security-sensitive because it contains a reset token.
3. Changing a header is not automatically a vulnerability; the security issue exists when the application uses attacker-controlled information to redirect or expose a sensitive token.
