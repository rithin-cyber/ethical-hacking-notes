# Objective

Understand Session Management.

# Session Workflow

```text
User logs in
↓
Server verifies credentials
↓
Server creates a session
↓
Server generates a Session ID
↓
Server stores the session on the server
↓
Server sends Set-Cookie
↓
Browser stores the cookie
↓
Browser sends the Cookie on future requests
↓
Server uses the Session ID to find the session
↓
User stays logged in
↓
User logs out
↓
Session is destroyed or invalidated
```

# Session ID

A Session ID is a unique value generated by the server that identifies a user's session.

The Session ID is usually stored in a cookie in the browser.

Example:

```http
Cookie: session=abc123
```

The Session ID does not contain the entire session. It acts as an identifier that allows the server to find the user's session data.

# Cookie Attributes

## HttpOnly

Prevents client-side JavaScript from accessing the cookie.

This helps reduce the risk of session-cookie theft through some XSS attacks.

Example:

```http
Set-Cookie: session=abc123; HttpOnly
```

---

## Secure

Tells the browser to send the cookie only over HTTPS connections.

This helps protect the cookie while it is being transmitted.

Example:

```http
Set-Cookie: session=abc123; Secure
```

---

## SameSite

Controls whether the browser sends the cookie with cross-site requests.

It helps reduce the risk of CSRF attacks.

Example:

```http
Set-Cookie: session=abc123; SameSite=Lax
```

# Session Timeout

A session timeout automatically expires an inactive session after a period of time.

Example:

```text
User logs in
↓
User remains inactive
↓
Session expires
↓
User must authenticate again
```

Purpose:

Reduce the risk of unauthorized use if a user leaves a device unattended.

# Session Fixation

Session fixation is a vulnerability where an attacker gets the victim to use a Session ID that the attacker already knows.

If the application does not generate a new Session ID after login, the attacker may be able to reuse the known Session ID.

Proper defense:

```text
Login
↓
Generate a new Session ID
↓
Use the new Session ID
```

# Session Hijacking

Session hijacking occurs when an attacker obtains another user's valid Session ID and uses it to impersonate that user.

Example:

```text
Victim's cookie:
session=abc123

Attacker obtains:
session=abc123

Attacker may attempt to use that session
```

Session IDs therefore need to be protected.

# Questions

## What is a session?

A session is a way for the server to remember a user across multiple requests after authentication.

## Why do websites need sessions?

Sessions allow a website to remember that a user is authenticated without requiring the user to log in again for every request.

## What is a Session ID?

A Session ID is a unique value that identifies a user's session. It is usually stored in a cookie and sent back to the server with future requests.

## What does HttpOnly do?

It prevents client-side JavaScript from accessing the cookie, helping reduce the risk of cookie theft through some XSS attacks.

## What does Secure do?

It tells the browser to send the cookie only over HTTPS.

## What does SameSite do?

It controls whether cookies are sent with cross-site requests and helps reduce CSRF risk.

## What happens when a session expires?

The session becomes invalid and the user usually needs to authenticate again.

## What is Session Fixation?

It is a vulnerability where the attacker knows or controls a Session ID before the victim logs in and the application fails to generate a new Session ID after authentication.

## What is Session Hijacking?

It is the use of another user's stolen or obtained Session ID to impersonate that user.

## Why should a new Session ID be generated after login?

A new Session ID helps prevent an attacker who knows a pre-login Session ID from reusing it after the victim authenticates.

## Why are Session IDs valuable to attackers?

A valid Session ID can allow an attacker to impersonate the associated user if the application accepts it as proof of the user's authenticated session.
